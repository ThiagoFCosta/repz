| # | Estado | Decisão | Motivo |
|---|---|---|---|
| **D32** | aprovada | A v1 fica congelada no GitHub Pages na tag `v1.0`. A partir do V1, o workflow deixa de publicar a `main` no Pages; a v2 só vai para a Netlify, e só quando o Thiago pedir. **(muda a v1: o job de deploy do CI)** | A `main` da v2 precisa do Supabase e não roda no Pages. Os dois continuam usando a v1 até migrarem (D42). |
| **D33** | aprovada | Rotas por caminho (`/treino`, `/historico`) com React Router 7 no lugar do hash router. Os E2E que navegam por `#/…` trocam a URL; as asserções não mudam. **(muda a v1: `roteador.ts`, `roteador.test.ts` e a URL nos E2E)** | O hash existia porque o GitHub Pages não faz fallback de SPA; a Netlify faz (`/* → /index.html`). |
| **D34** | aprovada | O estado de tela da v1 (`@preact/signals`) vira stores mínimas com `useSyncExternalStore`; a UI lê os dados com `useLiveQuery` do Dexie; o TanStack Query fica só para o que é online por natureza (rascunhos, códigos de compartilhamento, estado da sync, perfil remoto). | O app lê do Dexie (offline-first). Pôr TanStack Query entre a UI e o Dexie duplicaria cache. `@preact/signals-react` é frágil com React 18/19. |
| **D35** | aprovada | A Edge Function importa `src/dominio/` por caminho relativo, como o Prisma faz. Os imports internos do domínio passam a ter a extensão `.ts`; lint impede a volta; teste do grafo de imports da função. Plano B: cópia gerada (`agente:sync`). | O Deno exige extensão. É o mesmo arranjo que já está em produção no Prisma; dispensa pacote e cópia. |
| **D36** | aprovada | Preact → React de uma vez, dentro do V1, com os E2E da v1 como oráculo; nomes acessíveis mantidos. Onde o mockup muda texto ou navegação (5 abas + menu ☰), o passo do E2E muda. **Feito:** `goto('./#/treino')` → `goto('./')`, `goto('./#/plano')` → `goto('./plano')`, e os cliques nas abas Treino/Histórico/Plano → `irPara(page, 'Início' | 'Histórico' | 'Plano')` (`tests/e2e/navegacao.ts`: barra inferior ou menu ☰); nenhuma asserção mudou. **(muda a v1: passos de navegação dos E2E)** | Convivência dos dois frameworks dobraria bundle e trabalho; a UI vai ser redesenhada de qualquer forma. |
| **D37** | aprovada | Auth por e-mail + senha (como o Prisma), **cadastro fechado**; o Thiago convida pelo painel do Supabase. Sem magic link como entrada principal (fica como "esqueci a senha"). | Só dois usuários; senha funciona com o app instalado sem depender de abrir e-mail no celular. Aprovada na resposta à 16.3. |
| **D38** | aprovada | Plano de treino e plano alimentar são guardados como **um documento** (`estrutura jsonb`) por plano, com colunas só para o que muda ou é filtrado (ativo, início do bloco, ajuste, datas, origem). As tabelas `sessoes_template`, `exercicios_prescritos`, `dieta_dias`, `refeicoes`, `itens_refeicao` e `notas_dieta` do briefing viram partes desse documento. Um índice único parcial garante um único plano ativo por usuário. **(muda a v1: D2 trocou `ativo` por `meta.planoAtivoId`; no Postgres o índice parcial dá a mesma garantia)** | Os planos não mudam depois de importados (só início, ajuste e vínculos). Seis tabelas a mais seriam seis filas de sync, ordem de dependência e conflitos parciais, sem ganho de consulta. Os tipos da v1 (`Plano`, `SessaoTemplate`) continuam iguais. |
| **D39** | aprovada | Log de sugestões: **uma linha por exercício por treino**, criada quando a sessão é montada (a sugestão que pré-carrega a 1ª série) e fechada ao concluir (carga usada, `aceita`/`editada`/`ignorada`, resultado). O cartão "Para o próximo" não gera linha. `series.sugestao_kg` e `sugestao_aceita` da v1 migram para esse log. **(muda a v1: o modelo de `SerieRealizada`)** | A sugestão é recalculada a cada tela; logar todas multiplicaria linhas iguais. A que importa para a auditoria é a que o usuário viu no treino e aceitou ou não. |
| **D40** | aprovada | `alimentos` com base global (TACO 4ª ed. + rótulos genéricos, `user_id` nulo, só leitura) e cópias do usuário quando ele edita (`base_id`). **Substituições não são gravadas:** são calculadas na revisão e na tela a partir dos alimentos em cache. | O briefing pede "calculadas na importação e recalculadas quando a base ou as preferências mudam": calcular sempre na hora cumpre as duas coisas sem cache para invalidar (são 6 a 9 candidatos por grupo). |
| **D41** | aprovada | O conector serve **a cada usuário para a própria conta** (o Prisma é só do admin). A trava `agente_trava` aceita token com `client_id` só se aquele cliente foi aprovado pelo dono do token. | O briefing prevê o irmão com dados próprios; o isolamento entre os dois vem do RLS, que vale igual para o conector. |
| **D42** | aprovada | Migração da v1 pelo **backup JSON**: no 1º login sem dados, "Trazer seus dados da v1" → `migrarBackup()` → `deV1ParaV2()` → Dexie + fila. | v1 (github.io) e v2 (Netlify) são origens diferentes: a v2 não enxerga o IndexedDB da v1. |
| **D43** | aprovada | **Sem cifragem no cliente.** Os dados ficam protegidos por RLS entre usuários, conta do Supabase com 2FA e nenhum dado no git; quem administra o projeto (o Thiago) consegue ler os dados pelo painel, e o irmão é avisado disso. | Cifrar como o Prisma exigiria chave do agente, decifrar no pull e cálculos só no cliente, sem ganho real entre os dois.
